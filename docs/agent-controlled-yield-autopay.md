# Agent-Controlled Yield Autopay Design

最終更新: 2026-05-29 JST

## Revised Assumption

Subly の本番要件は「AI agent が元本を絶対に動かせないようにする」ことではない。

要件は次の通り:

- User/Agent Wallet は Kamino Vault の shares/kToken を持つ。
- Agent は通常の wallet 操作として Kamino から元本を withdraw できてよい。
- Subly402 の自動 API 決済体験では、Kamino で発生した yield を payment budget として使う。
- Subly は agent の通常 wallet 権限を奪わない。
- Subly は「Subly402 経由の API payment が yield budget に基づいて実行された」ことを検証・記録する。

つまり Subly は custody guard ではなく、まずは **yield-budgeted payment protocol** である。

## Product Definition

```text
Subly lets a user's AI agent pay for APIs through an x402-like flow,
using the yield generated by that user's Kamino Vault position.
```

日本語:

```text
Subly は、ユーザの AI エージェントが Kamino Vault で発生した yield を使って、
x402 のような API 決済を実行できるようにするプロトコル。
```

## Core Architecture

```text
User/Agent Wallet
  - owns USDC
  - owns Kamino Vault shares
  - can deposit/withdraw principal normally
  - signs Subly402 payments

Kamino Vault
  - accepts USDC
  - mints shares/kToken
  - yield accrues through exchange rate increase

Subly Budget Engine
  - tracks deposits, withdrawals, shares, exchange rate
  - computes accrued yield
  - reserves budget for API payments

Subly Facilitator / Paymaster
  - handles x402-like 402 flow
  - verifies payment requirements
  - sponsors SOL fees
  - settles payment or returns receipt

API Provider
  - returns 402 payment requirement
  - accepts Subly402/x402 payment receipt
```

## Key Distinction

Subly does not claim:

```text
Agent can never move principal.
```

Subly claims:

```text
Payments made through Subly402 are budgeted from accrued Kamino yield.
```

If the agent manually withdraws principal from Kamino or transfers USDC outside Subly402, that is outside the Subly402 payment protocol. This is acceptable if communicated clearly.

## Budget Accounting

Kamino shares are fungible, so Subly needs accounting rules.

```text
position_value = shares * exchange_rate
gross_yield = max(0, position_value + realized_yield_buffer - principal_basis)
spendable_yield =
  gross_yield
  - reserved_payments
  - fee_debt_usdc
  - safety_buffer
```

Definitions:

- `principal_basis`: user/agent deposits recognized by Subly as principal.
- `position_value`: current Kamino share value in USDC.
- `realized_yield_buffer`: USDC that Subly has classified as realized yield for API payments.
- `reserved_payments`: pending Subly402 payment intents.
- `fee_debt_usdc`: SOL fees paid by Subly, converted to USDC.
- `safety_buffer`: rounding/liquidity/fee buffer.

## Deposit Handling

### Subly API Deposit

1. Agent requests deposit intent.
2. Subly builds Kamino deposit transaction.
3. Agent signs.
4. Subly parses confirmed tx.
5. `principal_basis += actual_deposit_usdc`.
6. Shares remain in Agent Wallet.

### Kamino UI Deposit

1. User/Agent deposits into Subly Vault from Kamino UI using the same wallet.
2. Shares appear in the same wallet.
3. Subly sync detects new shares and/or deposit tx.
4. If deposit tx is parsed:
   - `principal_basis += actual_deposit_usdc`
5. If exact tx is not parsed:
   - user runs `activate/sync`
   - Subly records current position value as principal baseline

This supports the desired flow without requiring Guard custody.

## External Withdrawals

Because agent is allowed to withdraw principal, Subly must handle external wallet activity conservatively.

If Subly detects a Kamino withdrawal not initiated as `realize_yield`:

```text
principal_basis = min(principal_basis, current_position_value + realized_yield_buffer)
reserved_payments = cancel_or_reprice_if_needed
```

Simpler rule:

- Subly-initiated `realize_yield` keeps `principal_basis` unchanged.
- Any external withdraw decreases the baseline or triggers a required resync.
- Subly402 payments pause until sync confirms the new budget.

This prevents Subly from overestimating available yield after manual principal movement.

## Yield Realization

Subly should not withdraw from Kamino for every API call.

Recommended flow:

1. Budget Engine computes `spendable_yield`.
2. If payment buffer is below threshold, Subly builds a Kamino withdraw for yield-sized shares.
3. Agent signs the withdraw transaction.
4. Subly sponsor wallet pays SOL fee.
5. Resulting USDC goes to a dedicated yield payment buffer account.
6. If Kamino withdrawal queues, funds are not spendable until settled.

Dedicated buffer is strongly recommended:

```text
Agent main USDC ATA:
  normal wallet funds

Subly yield buffer token account:
  USDC classified as realized yield
  source for Subly402 payments
```

The buffer can still be owned by the Agent Wallet. Its purpose is accounting clarity, not custody restriction.

## Subly402 API Payment Flow

1. Agent calls paid API via Subly SDK.
2. API returns `402 Payment Required`.
3. Subly SDK sends payment requirement to Subly Facilitator.
4. Facilitator checks:
   - valid amount/token/network
   - API domain / merchant policy
   - per-request cap
   - daily/monthly cap
   - spendable yield
   - duplicate `payment_id`
5. If buffer is sufficient:
   - build SPL USDC transfer from yield buffer to merchant
   - Agent signs as token authority
   - Subly signs as fee payer
   - Facilitator settles and returns receipt
6. If buffer is insufficient but yield exists:
   - trigger background yield realization
   - return `budget_pending` or wait/retry
7. Agent retries original API request with payment proof.
8. API returns resource.

## x402 Compatibility Levels

### Level 1: x402-Compatible Payment

Use standard x402/Solana payment payloads and SPL transfers.

Pros:

- Works with existing x402 services.
- Easy merchant integration.

Limit:

- Standard x402 does not know whether funds came from Kamino yield.
- Subly can attest only for payments that passed through Subly SDK/facilitator.

### Level 2: Subly402 Receipt

API provider requires a Subly facilitator receipt:

```text
payment was approved by Subly budget engine
payment_id was not reused
amount <= spendable_yield
tx_signature settled
```

Pros:

- Stronger "yield-funded payment" proof.
- Better product differentiation.

Limit:

- Requires merchants to integrate Subly402 or accept Subly facilitator.

## Fee Payer

Subly should pay SOL fees.

Implementation:

- Transaction fee payer = Subly sponsor wallet or Kora.
- Token authority = Agent Wallet.
- Fee cost is converted to USDC and recorded as `fee_debt_usdc`.
- Future Subly402 budget subtracts `fee_debt_usdc`.

This supports:

```text
User does not need SOL.
Agent can still sign token movements.
Subly recovers infra cost from yield.
```

## What Is Technically Possible

Possible:

- Agent deposits into Kamino Vault through Subly API.
- User/Agent deposits through Kamino UI with the same wallet.
- Subly detects/syncs the position.
- Subly calculates accrued yield.
- Agent realizes yield into USDC.
- Subly sponsors SOL fee.
- Agent pays APIs through x402-like flow from yield budget.
- Agent can still manually withdraw principal outside Subly.

Not guaranteed by this design:

- Agent never touches principal.
- All wallet transfers are yield-funded.
- Standard x402 merchants can independently know payment source was Kamino yield.

Guaranteed/attested by Subly:

- Payments executed through Subly402 were authorized against Subly's yield budget ledger.
- Subly did not intentionally authorize API autopay beyond recognized yield budget.
- Receipts can show budget snapshot, payment id, merchant, amount, and tx signature.

## Recommended Positioning

Use:

```text
Yield-funded agent payments
Use Now, Pay Never
Agent API payments funded by Kamino yield
No principal drawdown through Subly402 autopay
```

Avoid saying:

```text
Agent cannot withdraw principal
Subly guarantees principal
All wallet payments are yield-only
```

The correct boundary is:

```text
Subly402 autopay is yield-budgeted.
The agent wallet remains user-controlled and can manage principal normally.
```
